# HPA 只会伸缩不会自愈？我设计了一个 K8s 应用自愈 Operator：KubeSentry

> 这是系列文章的第一篇。这个系列我会从零手写一个 Kubernetes Operator——KubeSentry，它能让集群里的应用"自己变强、自己疗伤"。本篇讲清楚：为什么做、解决什么问题、怎么设计。后续文章按模块拆解实现。

## 一、从一个凌晨三点的故障说起

假设你有这样一个服务部署在 K8s 上：

新版本上线十分钟后，5xx 错误率从 0.1% 飙到 15%。这时候会发生什么？

- **kubelet 说**：Pod 没挂啊，进程活着，探针也过，不归我管。
- **HPA 说**：错误率不是我的指标，我只看 CPU，现在才 30%，不扩容。
- **Deployment 说**：回滚？需要人来执行 `kubectl rollout undo`。

发现了吗？K8s 的每一个组件都在自己的职责边界内"正确地"工作，但**没有任何一个组件对"应用整体健康"负责**。凌晨三点，需要一个人爬起来，看 Grafana，判断，然后敲回滚命令。

KubeSentry 想做的就是把这个"人"的职责自动化：**声明式地告诉集群"什么状态算健康、出问题了按什么策略处理"，剩下的交给 Operator**。

## 二、现有方案的短板

调研了一圈主流方案，各有明确的能力边界：

**HPA（原生）**
- 只支持 CPU/内存等资源指标（自定义指标要装 Prometheus Adapter，配置繁琐）
- 纯比例控制，没有冷却窗口意识，流量尖峰下副本数反复横跳（震荡是经典问题）
- 对故障零响应

**KEDA**
- 指标源丰富（包括 Prometheus），解决了"用什么指标扩缩容"
- 但依然只有"伸缩"一只手，不管自愈

**Argo Rollouts / Flagger**
- 解决"发布过程的安全"（金丝雀、渐进式交付），但运行期故障自愈不在射程内

也就是说：**伸缩（KEDA）、发布安全（Flagger）、运行期自愈——第三块是空白**。KubeSentry 主攻第三块，同时用更好的伸缩算法补齐第二块短板。

## 三、KubeSentry 是什么

一句话：**一个基于 controller-runtime 的 Kubernetes Operator，通过自定义 CRD `App` 管理应用，提供多信号智能伸缩 + 分级故障自愈 + 金丝雀自动回滚。**

整体架构：

```
开发者 ──kubectl apply App CR──▶ API Server ──▶ Admission Webhook（校验+安全默认值）
                                     │
                                     ▼
                    ┌────────── KubeSentry Operator ──────────┐
                    │  App Controller（Reconcile 主循环）        │
                    │    ├── Scaler：多信号伸缩决策              │
                    │    ├── Healer：分级故障自愈引擎            │
                    │    └── 读写 Deployment / Service / Status │
                    └──────────────────────────────────────────┘
                                     ▲
                          Prometheus（QPS / P99 / 错误率）
```

用户写一个 `App` CR，就能获得：

```yaml
apiVersion: apps.sentry.io/v1alpha1
kind: App
metadata:
  name: order-service
spec:
  image: registry.example.com/order-service:v1.2.0
  replicas: 3
  scaling:
    minReplicas: 2
    maxReplicas: 20
    cooldownSeconds: 120          # 冷却窗口，防震荡
    metrics:
      - type: QPS
        target: "1000"            # 每 Pod 目标 QPS
      - type: P99Latency
        target: "200ms"
  health:
    strategy: graduated           # 分级自愈：扩容 → 降级 → 回滚
    canary:
      enabled: true
      observationSeconds: 300     # 新版本观察窗口
      errorRateThreshold: "0.01"  # 错误率超 1% 自动回滚
```

## 四、三个核心设计决策

### 决策 1：为什么是 Operator，而不是一个外部轮询服务？

完全可以写个 cron job 定期查 Prometheus 然后改 Deployment——但那只是"脚本的堆砌"。选 Operator 的理由：

1. **声明式**：用户描述期望状态（健康策略），而不是过程。这是 K8s 的灵魂，也是面试必考点。
2. **事件驱动**：Informer 机制让 Reconcile 只在资源变化时触发，比轮询优雅且省资源。
3. **原生集成**：`kubectl get app` 就能看到 Phase 和 Conditions，自愈动作直接以 Event 留痕，可审计、可追踪。

做这个项目的过程，就是吃透"控制器模式"的过程——ListWatch、DeltaFIFO、工作队列，这些面试高频词全都会在代码里亲手摸一遍。

### 决策 2：伸缩算法怎么防震荡？

HPA 震荡的根源是**无记忆的比例控制**。KubeSentry 加了三层防线：

1. **冷却窗口**：`now - lastScalingAt < cooldownSeconds` 时，拒绝一切缩容（扩容可以紧急放行——宁可多花钱，不可少容量）。
2. **迟滞带**：目标副本数与当前差值在 ±10% 内时不动作，避免"加一个又减一个"的抖动。
3. **缩容渐进**：每次最多缩 20%，扩容一步到位。不对称策略，因为扩太慢伤用户，缩太快伤稳定性。

多信号决策取"最紧急者"：`desired = max(ceil(replicas × current/target) for each metric)`，再被 min/max 和迟滞带约束。

### 决策 3：自愈为什么要"分级"？

最直觉的写法是：发现异常 → 立刻执行所有能做的动作（扩容 + 重启 + 回滚一起上）。**这是大忌**：动作互相干扰会破坏事故现场，让你永远不知道根因是什么。

KubeSentry 的分级自愈状态机：

```
L1 扩容（缓解流量型问题）──观察一个窗口──▶ 无效？
L2 降级（摘除不健康副本，切断对坏实例的流量）──观察──▶ 无效？
L3 回滚（回退到上一个健康 revision）
```

每次 Reconcile 只执行一级动作，动作之间必须有观察期。所有动作 Emit Kubernetes Event（reason 统一 `KubeSentry*` 前缀）并写回 Status——**自愈系统自己必须是可观测的**，否则它做出的错误决策你都没法审计。

## 五、安全也是一等公民（CKS 的落地点）

作为持有 CKA + CKS 的项目，安全设计不能只是嘴上说说：

- **Defaulting Webhook 自动注入安全上下文**：`runAsNonRoot`、`readOnlyRootFilesystem`、`drop ALL capabilities`、seccomp RuntimeDefault——受管应用默认就是 CKS 及格线以上的安全姿态
- **Validating Webhook**：禁止 `latest` 标签进生产、镜像必须显式 tag、伸缩范围合法性校验
- **Operator 自身**：distroless 镜像、非 root、RBAC 最小权限（拒绝通配符）
- **Webhook 证书**由 cert-manager 自动管理轮换
