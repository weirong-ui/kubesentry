# 给 K8s 加一个"自动值班员"：分级故障自愈引擎

> **更名说明**：本项目原名 **KubeSentry**，自 2026-11-03 起更名 **KubeStasis**（避免与既有项目重名）；CRD group 也于 11-04 由 `apps.sentry.io` 改为 `kubestasis.io`。前几篇文章里的旧名指的都是同一个项目，代码仓库现为 [github.com/weirong-ui/kubestasis](https://github.com/weirong-ui/kubestasis)。

> 系列第 3 篇[《为什么 HPA 会震荡？手写一个带冷却窗口的伸缩决策引擎》](https://juejin.cn/post/7703390672704274475)让 KubeStasis 学会了聪明地伸缩，但那有个隐含前提——**应用是健康的**。这篇处理应用不健康的时刻：CrashLoopBackOff、5xx 飙升、金丝雀发布翻车。我们要把它变成一个"自动值班员"：会扩容、会摘除、会回滚，以及最重要的——**知道什么时候该收手，打电话叫醒人类**。

## 一、半夜 3 点的 rollout undo

先看一个每个后端都经历过（或即将经历）的现场：

1. 凌晨 2:47，值班电话响了：订单服务 5xx 从 0.2% 飙到 40%
2. 2:49，爬起来开电脑、连 VPN、登录
3. 2:55，定位到 20 分钟前的一次发布（"就改了个小依赖"）
4. 3:02，`kubectl rollout undo deployment/order`
5. 3:08，5xx 回落，写字事故报告

从故障发生到恢复，**21 分钟**——这已经是反应很快的团队了。而这 21 分钟里损失的订单、烧掉的下游重试、污染的用户会话，都不会出现在复盘报告的"损失估算"里。

更扎心的是：**Kubernetes 其实一直在"自愈"，只是它修不了这个问题**。kubelet 检测到容器挂了会重启它，重启失败进入 `CrashLoopBackOff`，然后——继续重启，退避时间越拉越长。kubelet 的世界观里只有"单个容器"，它没有"版本"的概念。**一个坏镜像，重启一百次也是坏的**。`CrashLoopBackOff` 本质上是 kubelet 在说："我尽力了，该你们上了。"

所以 KubeStasis 的自愈引擎要做的事很明确：**在 kubelet 的能力边界之上，把"版本级"和"应用级"的故障接过来**。

## 二、先给故障分类：三个起点，而不是一条流水线

写自愈引擎最容易犯的错误，是把"分级"理解成流水线：先扩容，不行再降级，再不行回滚。**错**。对一个全量 CrashLoop 的应用做"扩容"，等于往火场里加人——多出来的 Pod 还是一起来一起崩，白白消耗集群资源，还稀释了关键信号（"扩容了怎么没好转"会让后面的判断更难做）。

正确的做法是：**故障模式决定起点，升级才走流水线**。KubeStasis 把故障分成三类：

| 故障类型 | 典型信号 | 起点等级 | 为什么 |
|---|---|---|---|
| **过载型** | 5xx 飙升 + Pod 全 Ready + P99 高 | L1 扩容 | 容量不够，加机器立竿见影，成本最低 |
| **局部故障** | 部分副本异常（5xx 集中在个别 Pod / 单节点） | L2 摘除 | 坏的是"少数派"，定点清除比全局动作精准 |
| **版本级故障** | 发布后全量 CrashLoop / 金丝雀窗口错误率越阈 | L3 回滚 | 根因在镜像，任何扩容摘除都是拖延 |

信号识别的实现（`healer.Inspect` 的核心部分）：

```go
// Inspect 采集 Pod 状态与应用指标，输出故障报告。
func (e *Engine) Inspect(ctx context.Context, app *appsv1alpha1.App,
	dep *appsv1.Deployment) Report {
	pods := &corev1.PodList{}
	// 只看本 App 管的 Pod：Deployment 的 selector
	if err := e.client.List(ctx, pods, client.MatchingLabels(dep.Spec.Selector.MatchLabels),
		client.InNamespace(app.Namespace)); err != nil {
		return Report{}
	}

	var signals []string
	crashing, notReady := 0, 0
	for _, pod := range pods.Items {
		for _, cs := range pod.Status.ContainerStatuses {
			// CrashLoopBackOff：kubelet 已经放弃的标志
			if cs.State.Waiting != nil && cs.State.Waiting.Reason == "CrashLoopBackOff" {
				crashing++
				signals = append(signals,
					fmt.Sprintf("CrashLoopBackOff(pod/%s, restarts=%d)", pod.Name, cs.RestartCount))
			}
			// OOMKilled：上一次退出是被内存杀的
			if cs.LastTerminationState.Terminated != nil &&
				cs.LastTerminationState.Terminated.Reason == "OOMKilled" {
				signals = append(signals, fmt.Sprintf("OOMKilled(pod/%s)", pod.Name))
			}
		}
		if !podutil.IsPodReady(&pod) {
			notReady++
		}
	}

	// 指标型信号：Prometheus 查错误率与 P99（实现见第 3 篇的查询模板）
	errRate := e.queryErrorRate(ctx, app)

	return e.diagnose(pods.Items, crashing, notReady, errRate)
}
```

`diagnose` 就是起点映射表：

```go
// diagnose：故障模式 -> 起点等级。这是整个引擎最重要的 20 行。
func (e *Engine) diagnose(pods []corev1.Pod, crashing, notReady int,
	errRate float64) Report {
	switch {
	// 版本级：发布后出现全量崩溃 —— 任何扩容摘除都是拖延
	case crashing == len(pods) && len(pods) > 0:
		return Report{Unhealthy: true, SuggestedLevel: L3Rollback,
			Signals: append([]string{"all pods crash-looping"})}

	// 局部故障：部分副本异常（含 Ready 但持续 5xx 的"半死"副本）
	case crashing > 0 || (errRate > e.errRateThreshold && notReady > 0):
		return Report{Unhealthy: true, SuggestedLevel: L2Isolate}

	// 过载型：Pod 都活着但错误率超标 —— 容量问题
	case errRate > e.errRateThreshold:
		return Report{Unhealthy: true, SuggestedLevel: L1ScaleUp}
	}
	return Report{Unhealthy: false}
}
```

注意 `crashing == len(pods)` 这个判断——**全量崩溃是版本级故障最可靠的指纹**。发布刚完成时 Pod 一定是全新的，如果它们全部进入 CrashLoop，除了镜像坏了几乎没有别的解释。

## 三、状态机：五条规则

> **实现状态说明**（2026-11-04 补）：这一节写于 P2 阶段，是**状态机的设计推演**，不是对当前代码的逐行描述。仓库 `main` 已落地的是：起点映射、每次 Reconcile 只做一个动作、由 `Status.LastHealLevel` / `LastHealAt` 驱动的冷却期复发升级、L3 回滚与防乒乓；`Degraded` 吸收态和"动作上限 3 次"仍是设计约束，尚未进代码。仓库里 [docs/STATUS.md](https://github.com/weirong-ui/kubestasis/blob/main/docs/STATUS.md) 是唯一可信的能力清单，别把设计稿当成已实现功能。第六节的时间线是推演结果，第七节已换成真集群实录。

有了起点，还需要一套状态机来管"动作的节奏"。自愈引擎最大的危险不是不动作，而是**乱动作**：误判一次就扩容、观察半分钟没好转就回滚、回滚完看指标波动又切回来——值班员亲手把事故变成事故连环现场。

KubeStasis 的状态机只有五条规则：

```
                 ┌──────────────────────────────────────────┐
                 │                                          │
    ┌────────┐   │  连续 2 个窗口 unhealthy                  │  观察窗结束仍不健康
    │ Stable │───┴──▶ ①防抖（streak ≥ 2）                    ▼
    └────────┘                                     ┌─────────────┐
         ▲                                         │   Healing   │
         │  观察窗内恢复 healthy                    │ L1 → L2 → L3│
         ├─────────────────────────────────────────┤             │
         │                                         └──────┬──────┘
    ┌──────────┐   动作数 ≥ 3 或 L3 后连续 2 窗口仍不健康    │
    │ Degraded │◀─────── ④上限与反乒乓 ────────────────────┘
    └──────────┘
         │  Event（设计中）+ Condition Degraded
         ▼
      打电话给人类（人工处理后重置）
```

1. **防抖**：连续 2 个观察窗口（默认各 60s）不健康才进入 Healing。单 Pod 重启、一次抓取抖动不该触发任何动作——第 3 篇的迟滞带管"数值上的小波动"，这条管"时间上的小波动"。
2. **起点映射**：进入 Healing 时按第二节的三分类选起点，不从 L1 傻跑。
3. **升级**：每个动作之后必须空出一个完整观察窗；窗口结束仍不健康才升到下一级。**一次只做一个动作**——同时"扩容 + 回滚"，你永远不知道是哪个起了作用，事故现场也被毁了。
4. **反乒乓**：L3 是终点，没有 L4。回滚之后如果连续 2 个窗口仍不健康，说明回滚目标也有问题，继续动作只会在两个坏版本之间来回切——进入 Degraded。
5. **上限**：单次事故最多 3 个自愈动作。超过就 Degraded、发 Event、写 Condition，然后**停下来等人类**。

第 5 条值得多聊两句。为什么是 3 次？因为自愈系统最坏的失败模式不是"没修好"，而是**无限重试**：扩容→摘除→回滚→又扩容……每次动作都真实地打在集群上，Pod 反复生死，事件刷屏，而根因纹丝不动。值班员最需要的不是"一个一直很努力的系统"，而是"一个知道放弃并大声喊人的系统"。**知道收手的自动化，才配叫自动化。**

Degraded 之后为什么不让它自己恢复重试？因为 **Degraded 本身就是最重要的告警信号**。如果引擎自己悄悄 reset 重新跑，人会永远看不到这条告警，而故障还在。解锁必须是显式的人工动作：改一次 `spec`，或者手工清掉 Condition。

## 四、三个动作的实现

### L1：紧急扩容（绕过冷却窗口）

第 3 篇留过一个扣子："冷却窗口该不该锁扩容？我倾向于不该。"这里兑现：自愈触发的扩容是**急诊**，不走伸缩引擎的冷却与迟滞，但尊重两条硬约束——`maxReplicas` 上限和 ×2 限速：

```go
func (e *Engine) scaleUp(dep *appsv1.Deployment, maxReplicas int32) *Action {
	cur := int32(1)
	if dep.Spec.Replicas != nil {
		cur = *dep.Spec.Replicas
	}
	// ×2 限速 + 上限，与 scaler 的扩容刹车保持一致
	want := min(cur*2, maxReplicas)
	if want <= cur {
		return nil // 已在 maxReplicas，L1 无空间 —— 直接告诉状态机升级
	}
	dep.Spec.Replicas = &want
	return &Action{Level: L1ScaleUp, Name: "scale-up",
		Detail: fmt.Sprintf("%d -> %d replicas (emergency)", cur, want)}
}
```

注意返回 `nil` 的情况：如果已经在 `maxReplicas`，扩容没有空间，这不是"动作失败重试"，而是"L1 注定无效"——状态机应该跳过观察窗直接升级。**动作执行的结果分类（成功/无效/失败）比动作本身更重要**，后面 Degraded 的判断全靠它。

### L2：定点摘除

对"部分副本坏"的场景，动作是 delete 掉异常 Pod：

```go
func (e *Engine) isolate(ctx context.Context, pods []corev1.Pod) *Action {
	var removed []string
	for _, pod := range pods {
		if !isUnhealthy(pod) { // CrashLoop / OOM / Ready 但被诊断异常
			continue
		}
		if err := e.client.Delete(ctx, &pod); err == nil {
			removed = append(removed, pod.Name)
		}
	}
	return &Action{Level: L2Isolate, Name: "isolate",
		Detail: fmt.Sprintf("removed unhealthy pods: %v", removed)}
}
```

第一版我写的是"给坏 Pod 打标签，然后改 Service selector 摘流量"。写的时候就很别扭，因为**它是在重新发明 readiness 探针**：NotReady 的 Pod 本来就不在 Endpoints 里，Service 根本不会给它发流量。对 CrashLoop 的 Pod，"摘除流量"是伪需求——它压根没收到过流量。

L2 真正有意义的场景是两类：

- **节点级故障**：Pod 本身没病，是宿主机坏了（磁盘满、内核 panic 前兆）。delete Pod 触发重建，新 Pod 被调度到健康节点，问题消失。
- **"半死"副本**：Ready 但持续 5xx 的僵尸（连接池死了但探针还过）。这类 Pod readiness 探针发现不了，定点 delete 是唯一手段。

这就是为什么 `diagnose` 里局部故障的判据是"部分异常"而不是"有异常"——**动作必须和诊断对齐，否则 L2 就退化成重启大法**。

### L3：回滚，但要回滚到 CR 层

回滚的实现里藏着本篇我最喜欢的一个设计决策：

```go
// Rollback 读取 ReplicaSet 修订历史，回退到上一个版本的镜像。
func (e *Engine) Rollback(ctx context.Context, app *appsv1alpha1.App,
	dep *appsv1.Deployment) (*Action, error) {
	rsList := &appsv1.ReplicaSetList{}
	if err := e.client.List(ctx, rsList, client.InNamespace(app.Namespace),
		client.MatchingLabels(dep.Spec.Selector.MatchLabels)); err != nil {
		return nil, err
	}

	// 按 revision annotation 找到上一个非当前版本的 RS
	prev, ok := previousRevision(rsList, dep)
	if !ok {
		return nil, fmt.Errorf("no previous revision to roll back to")
	}
	prevImage := containerImage(prev.Spec.Template)
	if prevImage == dep.Spec.Template.Spec.Containers[0].Image {
		return nil, fmt.Errorf("previous revision has same image, cannot roll back")
	}

	// 关键：不改 Deployment，改 App.Spec.Image
	app.Spec.Image = prevImage
	if err := e.client.Update(ctx, app); err != nil {
		return nil, err
	}
	return &Action{Level: L3Rollback, Name: "rollback",
		Detail: fmt.Sprintf("image -> %s (revision %d)", prevImage, revisionOf(prev))}, nil
}
```

> 上面是简化示意：落地版本返回的是 `revision`（`0` 表示没有可退的版本），且所有 spec 写路径都用 `RetryOnConflict + Merge Patch`，原因见第八节坑 1。

两种写法的区别：

- **改 Deployment**（`kubectl rollout undo` 的做法）：直接、快，但 KubeStasis 下一轮 Reconcile 一看 Deployment 和 `app.Spec.Image` 不一致，会**把它改回来**——你刚回滚完，自己的控制器又把坏镜像推上去了。要么就得在 Reconcile 里加各种例外逻辑。
- **改 App.Spec.Image**：让**声明式自己完成回滚**。Spec 变了 → Reconcile 发现 Deployment 与 Spec 不一致 → 对齐。一行例外代码都不用写，而且审计记录（谁在什么时候把镜像改回了什么）天然留在 CR 的 resourceVersion 里。

这就是 Operator 模式的好处：**你的控制器只有一个"把现实对齐到期望"的逻辑，所有修复都应该是"修改期望"，而不是"修改现实"**。绕过自己的控制器改现实，等于亲手拆自己的地基。

顺带说坑：`previousRevision` 依赖 ReplicaSet 的 `deployment.kubernetes.io/revision` annotation。如果 Deployment 的 `.spec.revisionHistoryLimit` 被调成了 0（有些人为了"省 etcd"），修订历史就没了，回滚无从谈起——L3 必须处理这个分支：返回 `revision=0`，控制器发一条 `KubeStasisCanaryFailed` 告警后保持现状，**不空转、不 panic**。

## 五、金丝雀观察窗口：把回滚从"救火"提前到"体检"

上面所有逻辑都是"病了再治"。金丝雀窗口做的是"发布时就盯着"：

```yaml
health:
  canary:
    enabled: true
    observationSeconds: 300    # 发布后观察 5 分钟
    errorRateThreshold: "0.02" # 错误率超过 2% 就回滚
```

Reconcile 主循环里它是优先级最高的检查（对应设计文档 4.1 的第 4 步）：

```go
// 金丝雀窗口内：镜像刚变更，其余动作全部让路
if healer.InCanaryWindow(app) {
	if bad := healer.CheckCanary(ctx, app); bad {
		// 直达 L3，跳过防抖 —— 发布窗口的错误率抬升不需要再等 2 个窗口确认
		act, err := healer.Rollback(ctx, app, dep)
		// Event + Status.RollbackRevision 写回...
		return ctrl.Result{RequeueAfter: time.Minute}, err
	}
	// 窗口内不伸缩、不自愈，专心观察
	return ctrl.Result{RequeueAfter: 30 * time.Second}, nil
}
```

两个细节：

- **窗口起点是 Status 而不是 annotation**：写这篇时我设想给 Deployment 打 `last-rollout-at` annotation，落地时发现没必要——控制器在检测到镜像变更时已经会写 `Status.LastImageChangeAt`，`InCanaryWindow` 直接拿它加 `observationSeconds` 算窗口即可。**能放进 Status 的状态就别再往对象上贴标签**，否则两套时间戳早晚不一致。
- **错误率查询的窗口是个仍未关掉的坑**：`rate(http_requests_total{...}[5m])` 会把发布前的健康样本也卷进来，稀释错误率。当前实现由 `ErrSource` 的查询窗口决定粒度（默认 `--prometheus-window`），还没有做到"只统计发布时间之后的增量"——这个限制我写在 [docs/STATUS.md](https://github.com/weirong-ui/kubestasis/blob/main/docs/STATUS.md) 里，不假装已经解决。
- **查不到数据时不回滚**：`CheckCanary` 在指标源不可用或返回空值时返回 false，宁可放过也不误回滚；窗口内错误率越阈但**没有更早版本可退**时，只发 `KubeStasisCanaryFailed` 告警，不空转。
- **金丝雀窗口跳过防抖**：发布是已知的风险时刻，窗口内的错误率抬升几乎不可能是误报，多等 2 分钟只是多烧 2 分钟流量。防抖保护的是稳态，不是变更窗口。

## 六、该重试还是该放弃：三条时间线

把状态机跑起来，参数：tick = 60s，防抖 = 2 窗口，动作上限 = 3。下面四条时间线是**设计推演**（用纯函数状态机跑出来的，不是线上压测数据），用来把"该重试还是该放弃"这条边界想清楚；真集群实测结果见第七节：

**场景 1：发布坏镜像，全量 CrashLoop（起点 L3）**

| 时间 | 状态 | 事件 |
|---|---|---|
| t+01:00 | Stable | unhealthy ×1（新 Pod 开始崩溃） |
| t+02:00 | Stable | unhealthy ×2 → 进入 Healing |
| t+03:00 | Healing | **L3 回滚**（`App.Spec.Image` 改回 v1） |
| t+04:00 | Healing | 观察窗：v1 滚动中，仍 unhealthy，不升级（反乒乓） |
| t+05:00 | Stable | **RECOVERED** |

从故障出现到恢复 5 分钟，其中人工参与时间为 **0**。

**场景 2：流量过载，5xx 飙升（起点 L1）**

t+02 确认 → t+03 **L1 扩容**（3→6）→ t+04 RECOVERED。4 分钟，一个动作。

**场景 3：L1 无效的深水区（升级链 L1→L2→L3）**

流量过载背后其实是当前版本的内存慢泄漏，扩容只是续命：

t+03 L1 扩容 → t+04 观察窗仍不健康 → 升级 → t+05 L2 摘除 → t+06 仍不健康 → 升级 → t+07 **L3 回滚** → t+08 RECOVERED。8 分钟、3 个动作，每个动作之间都有一个完整的观察窗。**升级慢是特性不是缺陷**——每一次升级都应该伴随"上一级为什么没用"的判断，秒级连招只会把三种动作搅成一锅粥。

**场景 4：回滚目标也坏了（Degraded）**

| 时间 | 状态 | 事件 |
|---|---|---|
| t+03:00 | Healing | L3 回滚到 v1 |
| t+04:00 | Healing | 观察窗仍 unhealthy（回滚后第 1 个窗口） |
| t+05:00 | **Degraded** | 回滚后连续 2 窗口不健康 → **放弃，发告警 Event 并写入 Degraded（设计态，待落地）** |
| t+05 之后 | Degraded | 不再有任何自动动作，等人类 |

对照一下第一节的人工流程：21 分钟（而且需要一个活人凌晨爬起来）。场景 1 是 5 分钟、0 人工；场景 4 这种"两个版本都坏"的绝境，自动值班员 3 分钟内就完成了放弃决策并发出了高置信度告警——**值班同学看到的不再是"5xx 飙升"这种需要定位的模糊告警，而是"我已经试过回滚了、两个版本都不行、大概率是依赖问题"的行动建议**。这才是自动化对 on-call 的真正价值：不是替你修，是替你把排查做完。

## 七、真集群里跑一遍

设计推演说完，看真实结果。下面是仓库 [docs/demo/02-self-healing.md](https://github.com/weirong-ui/kubestasis/blob/main/docs/demo/02-self-healing.md) 的实录（Docker Desktop Kubernetes v1.36.1；`--heal-cooldown=30s` 是演示用的小冷却，生产默认 3m）。完整命令和原始输出在文档里，CI 的 kind e2e 也跑同一条链路：

```bash
# 健康版本先跑稳：healdemo = kubestasis-demoapp:v1，2 副本，health.strategy=graduated
# 发布一个启动即退出的坏版本
kubectl patch app healdemo --type=merge -p '{"spec":{"image":"kubestasis-demoapp:crash"}}'
```

```
T+0     发布 crash 镜像，两个 Pod 进入 Error/CrashLoopBackOff
T+150s  KubeStasisHealAction  L2 Isolate: deleted 1 unhealthy pod(s): [healdemo-798bd556d-n9w9h]
        # 删除后重建的 Pod 依旧 CrashLoop —— L2 治不好"版本本身坏了"
T+171s  KubeStasisHealAction  L3 Rollback: image kubestasis-demoapp:crash -> kubestasis-demoapp:v1 (revision 1)
        # 冷却期内故障复发 → 自动升级到 L3，从 ReplicaSet 修订历史找到上一版本镜像
T+173s  KubeStasisReconcile   app available: 2/2 replicas ready
```

终态 `status.phase=Stable`、`currentImage=kubestasis-demoapp:v1`、`lastHealLevel=2`。

有个值得停下来看的差别：**真实故障起点是 L2，不是第六节推演里的 L3**。`Inspect` 当时看到的是"部分 Pod 崩、部分正在重建"，判成局部故障；L2 摘除治不好，冷却期内复发才升级到 L3 回滚。这反而印证了第二节那句"故障模式决定起点、升级才走流水线"——只是真集群里的信号比纸面推演脏得多，别指望一上来就能识别出"全量崩溃"。

事件 reason 统一前缀便于运维检索：`KubeStasisScaleUp` / `ScaleDown` / `HealAction` / `Rollback` / `CanaryFailed` / `Reconcile` / `Error`。`kubectl describe app healdemo` 里每一步都有留痕，这就是"值班员的工作日志"。

## 八、五个踩过的坑

**坑 1：回滚乒乓（kind CI 真抓到过）。** 一层是外部的：v1→v2（坏）→回滚 v1→发布系统又推 v2→又回滚……自愈引擎和发布系统打架。更隐蔽的是内部一层：L3 从 ReplicaSet 修订历史里挑"上一个不同镜像"，如果历史里修订号最高的那一版**恰好就是正在崩溃的坏镜像**，回滚会把自己又滚回事故现场。对策是把 `Inspect` 报出的 `BadImages` 作为 `exclude` 传进 `Rollback`，选版时同时排除当前镜像与坏镜像；没有候选就返回 `revision=0`，只告警不空转。同一个 bug 还带出第二个坑：回滚写 `App.Spec.Image` 会和 status 回写撞 `the object has been modified`，所以全部 spec 写路径统一改成 `RetryOnConflict + Merge Patch`（每次重试重新 Get 最新对象重算）。**自动化系统之间的冲突比自动化本身更危险。**

**坑 2：全量 CrashLoop 时做 L2。** 上面说过：NotReady 的 Pod 不在 Endpoints 里，摘除是伪需求。诊断必须区分"摘不掉流量的坏"和"还在接流量的坏"。

**坑 3：观察窗内插动作。** 曾经为了"加速"，在回滚观察窗内顺手把副本也扩了。结果回滚的滚动更新和扩容的滚动更新叠加，Pod 数量飙到 max，节点被打爆。**一次 Reconcile 只允许一个动作**，写进状态机而不是靠自觉。

**坑 4：把 kubelet 的重启计数当故障指标。** Pod 重启 3 次可能是启动慢（JVM 预热超时），重启 30 次才是真崩。单次窗口的 restartCount 增量比绝对值可靠，配合防抖一起用。

**坑 5：Degraded 没接告警。** 状态机画得再完善，如果放弃信号没人订阅，等于值班员把电话打在没人接的分机上。Event 只在集群内可见，生产上要接 Alertmanager 或 webhook 出去——当然，这个坑的前提是 Degraded 真的落地了，目前它还在设计稿里（见第三节说明）。放到第 7 篇"上生产"里一起做。

## 九、下一篇

值班员上线后，KubeStasis 已经"会治病"了。但它的每次出手都在真实修改集群——如果有人建了个 `minReplicas > maxReplicas` 的 App，或者镜像没打 tag 就 apply 进来，最好在入口就拦住，而不是等 Reconcile 报错。这部分（Admission Webhook，P3）已经在仓库里落地，文章排在后面。

**下一篇先讲一个更"别人不会写"的东西**：《图解 client-go Informer：手写一个 mini-Informer 才敢说懂》——不依赖 client-go 手写 ListWatch → DeltaFIFO → Store → WorkQueue，把"为什么要压缩、断线为什么重列、两个队列为什么不能合并"讲透。自愈和 Webhook 的中文文章很多，手写 Informer 是把"能背八股"变成"能画数据流"的分水岭。

代码在 [github.com/weirong-ui/kubestasis](https://github.com/weirong-ui/kubestasis)（`internal/healer/`、`pkg/miniinformer/`），真实能力清单见 [docs/STATUS.md](https://github.com/weirong-ui/kubestasis/blob/main/docs/STATUS.md)。觉得有用点个赞，仓库点个 star 追更不迷路；如果你觉得"动作上限 3 次太保守"或者"Degraded 应该允许自动重试"，非常欢迎评论区来辩——这两条目前还停留在设计稿，正是最该被挑战的地方。
